# ADR 0016: 홈 유형 필터 분리 — 저장 태그는 정렬(sort_tags), 필터는 요청 파라미터

## 상태 (Status)

Accepted (2026-10-15). [ADR 0011](0011-place-search-and-filter-sort.md)의 **"필터 상태는 서버 저장"** 결정을 대체한다. 0011의 나머지 결정(검색 별도 엔드포인트, ILIKE 부분일치, 매칭 우선 정렬과 커서 확장)은 그대로 유효하다.

## 배경

ADR 0011은 회원이 고른 연습유형을 `member.filter_tags`에 저장하고, 목록·검색에서 **매칭 장소를 앞에 두는 정렬**로 썼다. 이후 [스펙 019](../specs/019-refinements-1.md) 2번에서 이를 **매칭 장소만 주는 필터**로 바꿨다(9dc4505, 미배포).

그런데 아직 코스 수가 적어서, 필터를 저장한 회원은 앱에 들어오자마자 매칭 장소가 없는 **빈 화면**을 자주 보게 된다. 목표는 빈 화면을 최대한 덜 보여주는 것이다. 정할 것은 두 가지였다.

1. 첫 진입 화면에서 저장된 값을 정렬로 쓸지, 필터로 쓸지.
2. 사용자가 직접 거는 필터의 상태를 어디에 둘지(서버 저장 vs 앱 로컬).

## 결정

- **저장된 값은 정렬 기준으로만 쓴다.** 매칭 장소가 먼저, 나머지도 전부 나온다(0011과 같은 동작). 9dc4505를 되돌렸다. 저장 값의 쓰임에 맞게 컬럼·API 이름을 `filter_tags` → **`sort_tags`**로 바꾼다(V27, `PUT /members/me/sort-tags`).
- **필터는 요청 파라미터로 받는다.** 앱이 필터 선택을 로컬에 저장하고 목록·검색·마커 요청에 `practiceTypes`(`PracticeType` 목록)를 보낸다. 파라미터가 있으면 매칭 장소만 준다. 서버는 필터 상태를 저장하지 않는다.
- **필터와 정렬은 독립적으로 함께 적용된다.** 필터는 "무엇을 보여줄지", 정렬은 "어떤 순서로"라서, 필터를 걸어도 그 결과 안에서 `sort_tags` 매칭 장소를 먼저 둔다.
- **목록·검색 쿼리는 각각 하나다.** 필터와 정렬 기준을 모두 파라미터로 받고 쓰지 않는 쪽은 플래그로 끈다. 정렬 키는 항상 `(matched, distance, id)`이고 커서 `sortValue`도 `matched|distance` 한 형식이다(정렬이 없으면 matched가 모두 0). 거리만 있는 옛 커서는 `matched=0`으로 받아 배포 순간에도 스크롤이 끊기지 않게 한다.
- 앱의 초기 필터값은 없다. 첫 진입은 항상 정렬(또는 거리순)이라 매칭 코스가 없어도 빈 화면이 나오지 않는다.
- 옛 경로 `PUT /members/me/filter-tags`는 앱 전환 전까지 별칭으로 남긴다(deprecated, 호출 로그). 앱이 새 경로를 쓰는 버전으로 배포되면 별도 이슈에서 지운다.
- `sort_tags`는 지금처럼 앱이 온보딩 후 PUT으로 채운다. 서버가 온보딩 연습유형을 자동 복사하지 않는다.

## 결과

### 긍정적

- 첫 진입 화면이 항상 전체 장소를 보여줘, 코스가 적은 지금 빈 화면이 크게 줄어든다.
- 필터는 사용자가 건 때만 적용되고, 요청만 보고 결과를 알 수 있다(같은 요청이면 같은 결과).
- 서버만 먼저 배포해도 하위호환이다 — 파라미터 없는 요청은 이전과 같은 결과이고, 옛 PUT도 동작한다.

### 부정적

- 쿼리 하나가 `OR` 플래그로 조건을 켜고 끄므로, 조건별로 고정된 쿼리보다 실행 계획이 덜 최적일 수 있다. 지금 데이터 규모(수백~수천 건)에선 영향이 없고, 느려지면 모드별 쿼리로 다시 나눌 수 있다.
- `@Query`에는 컴파일 타임 상수만 들어가 매칭 술어를 필터용·정렬용 두 상수로 둬야 한다(파라미터 이름만 다름). 같은 규칙인지는 테스트로 지킨다.
- 필터 상태가 앱 로컬이라 재설치·기기 변경 시 필터가 초기화된다. 첫 진입은 필터 없음이 기본이라 문제로 보지 않는다.
- 옛 PUT 별칭과 그 DTO를 앱 전환 뒤 따로 지워야 한다.

### 중립적

- 0011의 "필터는 로그인 전용" 제약이 목록·마커에서는 없어진다. 비로그인도 파라미터를 보낼 수 있다(검색은 JWT 필수 유지). 비로그인 사용자에게 필터 UI를 보여줄지는 앱이 정한다.

## 검토한 대안

### 대안 1 — 저장 필터로 매칭 장소만 반환 (9dc4505) — 되돌림

필터 의미에 충실하지만, 코스가 적은 지금은 저장된 필터 때문에 첫 화면부터 비는 경우가 많다. 사용자가 필터를 건 기억이 없어도 결과가 줄어 보인다. 목표(빈 화면 최소화)와 맞지 않아 되돌렸다.

### 대안 2 — 필터도 서버 저장, 별도 컬럼 추가

정렬용과 필터용을 각각 서버에 저장하는 안. 기기 간 유지는 되지만 필터 상태를 바꿀 때마다 PUT이 필요하고, 저장된 필터가 다음 진입에 다시 빈 화면을 만들 수 있어 배제했다.

### 대안 3 — 모드별 쿼리(기본·정렬·필터, 필요 시 필터+정렬)

조건이 고정돼 실행 계획이 가장 좋지만, 필터와 정렬을 함께 쓰려면 목록·검색 각각 4벌이 되고 서비스에 모드 분기·커서 형식 분기가 생긴다. 데이터 규모상 성능 이득이 없어 하나의 쿼리로 합쳤다.

### 대안 4 — 이름을 `preferred_practice_types`로 변경

데이터 의미(선호 연습유형)를 담아 정렬 외 용도에도 맞는 이름이지만, 기존 `filter_tags`·코스 `tags`와의 일관성을 위해 `sort_tags`를 택했다.
