# ADR 0011: 장소 검색·필터 정렬 전략 — 별도 엔드포인트 · ILIKE 부분일치 · 서버 저장 필터

## 상태 (Status)

Accepted (2026-07-27). 초기엔 클라 소유(B안)로 결정했으나, 회의에서 "비로그인은 필터 불가(로그인 전용)"로 요구가 바뀌며 B안의 근거가 사라져 **서버 저장(A안)으로 확정**했다(구현 완료). 아래 결정은 최종본이며, 대안 3이 채택된 안이다.

## 배경

홈에서 시군구 주소로 장소(코스+주차장)를 찾는 **검색**과, 레벨에 맞는 코스를 앞에 노출하는 **정렬 필터**가 필요해졌다([스펙 007](../specs/007-course-search-filter.md)). 결정할 것이 세 가지였다:

1. 검색을 기존 뷰포트 목록 API에 끼울 것인가, 별도 엔드포인트로 만들 것인가.
2. 텍스트 매칭을 무엇으로 할 것인가(LIKE vs full-text vs 외부 검색엔진).
3. 필터 선택 상태를 어디에 저장할 것인가(서버 DB vs 클라이언트 로컬). 초기엔 "비로그인도 필터 사용"이 요구였으나, 이후 "검색은 로그인 전용, 필터도 로그인 전용"으로 바뀌며 서버 저장이 유력해졌다.

## 결정

- **검색은 별도 엔드포인트** `GET /api/v1/places/search`로 만든다. 기존 뷰포트 목록(`GET /api/v1/places`)은 bbox 4개+현위치가 전부 필수인 뷰포트 전제 설계라, 전국 대상 검색을 끼우면 파라미터 조건부 필수·커서 의미 분기가 한 API에 섞인다. 응답 아이템(`PlaceListItem`)과 `CursorPage`는 재사용한다.
- **텍스트 매칭은 PostgreSQL `ILIKE` 부분일치**(`address ILIKE '%kw%'`, `%`·`_` 이스케이프)로 시작한다. 데이터가 수백~수천 건 규모라 인덱스 없이 충분하고, 느려지면 **pg_trgm(trigram) 인덱스**를 추가한다(쿼리 변경 없이 인덱스만). 장소명(name) 검색 확장은 `OR name ILIKE` 한 줄이면 된다.
- **필터 상태는 서버 저장**이다. 회원의 선택 연습유형을 `member.filter_tags`(jsonb `List<PracticeType>`, 마이그레이션 V9)에 저장하고 `PUT /api/v1/members/me/filter-tags`로 전체 교체한다. 목록·검색은 **인증된 요청일 때만** 저장된 필터로 매칭 우선 정렬하며(옵셔널 JWT — 검색은 로그인 필수), 비로그인이면 거리순만. 쿼리 파라미터로 필터를 받지 않는다(로그인 전용 자연 강제).
  - **카테고리는 여전히 클라 전용 UX 개념**이다. 클라가 카테고리→연습유형 매핑·온보딩 기본값 계산을 하고 **풀린 `PracticeType` 리스트**를 PUT으로 보낸다. 서버는 카테고리를 모르고 연습유형만 저장·매칭한다(서버 측 카테고리 enum 없음).
  - 기존 회원 backfill은 하지 않는다(다음 홈 진입 시 클라가 PUT으로 세팅).
- **정렬은 "필터 매칭 우선 → 현위치 거리 → id"** 3-키이며, 필터는 필터링이 아니라 정렬이다(비매칭도 후순위로 전부 노출). 커서 keyset을 `(matched, distance, id)`로 확장한다 — [ADR 0010](0010-list-query-cursor-postgis.md)의 커서 패턴에 정렬 키만 추가.

## 결과

### 긍정적

- 필터가 서버에 남아 **재설치·기기 변경에도 유지**되고 기기 간 일관된다.
- "필터는 로그인 전용" 요구가 **자연 강제**된다 — 비로그인은 저장된 필터가 없어 거리순, 파라미터로 우회할 여지도 없다.
- 인증 요청이면 매칭 place 우선 정렬, 비필터(비로그인·빈 필터)면 기존 거리순 쿼리 그대로라 하위 호환.
- 서버 측 카테고리 enum·개념이 없다 — 기존 `PracticeType`·태그 테이블만으로 저장·매칭.

### 부정적

- V9 마이그레이션·`PUT` 엔드포인트·목록/검색의 옵셔널 JWT 처리 등 서버 구현이 늘었다(B안 대비).
- 기존 회원은 backfill을 안 해서, 클라가 처음 PUT하기 전까지는 필터가 비어 거리순으로 노출된다(무해, 다음 진입 시 세팅).
- `%kw%` 패턴은 인덱스를 못 타므로 데이터가 커지면 pg_trgm 도입 시점을 챙겨야 한다.

### 중립적

- 검색·목록 두 엔드포인트가 정렬·커서 로직을 공유하므로 쿼리 구성은 공통화가 필요하다.
- `PARKING` 연습유형이 두 카테고리(도심 기본·넓은 공간)에 겹치지만, 클라가 풀어 보낸 값이 합집합(집합)이라 서버 저장·매칭엔 영향이 없다.

## 검토한 대안

### 대안 1 — 기존 목록 API에 keyword 파라미터 추가

엔드포인트 1개 유지가 장점이나, bbox·현위치 필수인 기존 검증을 조건부로 바꿔야 하고 "뷰포트 모드/검색 모드"가 한 API에 섞여 커서 의미까지 분기된다. 검증된 API를 건드리는 회귀 리스크도 있어 배제.

### 대안 2 — PostgreSQL full-text search·외부 검색엔진(Elasticsearch 등)

형태소·관련도 랭킹이 강점이나, 시군구 주소 부분일치라는 요구에는 과하다. 운영 부담(별도 인프라·색인 동기화) 대비 이득이 없어 배제. 자동완성·장소명 유사 검색이 커지면 재검토.

### 대안 3 — 필터 서버 저장 (member.filter_tags 컬럼 + PUT API + 옵셔널 JWT) ✅ 채택

재설치·기기 변경에도 필터가 유지된다. 초기엔 "비로그인도 필터 사용" 요구 때문에 클라가 로컬+파라미터 경로를 어차피 구현해야 해 이중화 부담으로 보류(B안 선택)했으나, **"필터 로그인 전용"으로 요구가 바뀌자** 비로그인 경로 자체가 사라져 이중화 우려가 없어졌다. 서버 저장이 로그인 전용을 자연 강제하고 상태를 한 곳에 두므로 **최종 채택**했다.

### 대안 4 — 서버 측 카테고리 enum(FilterCategory 5종)

카테고리를 서버 enum으로 두고 파라미터·검증·연습유형 확장을 서버가 담당하는 안. 선택 상태 복원 모호성(PARKING이 두 카테고리에 겹침) 때문에 필요해 보였으나, **필터 상태(연습유형 집합)는 서버가 저장(대안 3, 채택)하되 "어느 카테고리를 켰는지"라는 선택 UI 상태만 클라가 로컬로 관리**하도록 확정되며 복원이 서버 일이 아니게 됐다. 카테고리는 사용자 이해를 돕는 클라 UX 그룹핑일 뿐이고 혼합 선택은 연습유형 합집합이라, 서버는 기존 `PracticeType`만 알면 충분해 **배제**했다.
