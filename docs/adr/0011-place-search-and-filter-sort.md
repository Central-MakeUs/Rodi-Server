# ADR 0011: 장소 검색·필터 정렬 전략 — 별도 엔드포인트 · ILIKE 부분일치 · 클라 소유 필터

## 상태 (Status)

Accepted (2026-07-23) — 클라 소유 필터(B안)는 클라 팀 합의 전제, 불발 시 대안 3(서버 저장) 재검토

## 배경

홈에서 시군구 주소로 장소(코스+주차장)를 찾는 **검색**과, 레벨에 맞는 코스를 앞에 노출하는 **정렬 필터**가 필요해졌다([스펙 007](../specs/007-course-search-filter.md)). 결정할 것이 세 가지였다:

1. 검색을 기존 뷰포트 목록 API에 끼울 것인가, 별도 엔드포인트로 만들 것인가.
2. 텍스트 매칭을 무엇으로 할 것인가(LIKE vs full-text vs 외부 검색엔진).
3. 필터 선택 상태를 어디에 저장할 것인가(서버 DB vs 클라이언트 로컬). 비로그인 사용자도 필터를 쓸 수 있어야 한다는 요구가 결정에 영향을 줬다.

## 결정

- **검색은 별도 엔드포인트** `GET /api/v1/places/search`로 만든다. 기존 뷰포트 목록(`GET /api/v1/places`)은 bbox 4개+현위치가 전부 필수인 뷰포트 전제 설계라, 전국 대상 검색을 끼우면 파라미터 조건부 필수·커서 의미 분기가 한 API에 섞인다. 응답 아이템(`PlaceListItem`)과 `CursorPage`는 재사용한다.
- **텍스트 매칭은 PostgreSQL `ILIKE` 부분일치**(`address ILIKE '%kw%'`, `%`·`_` 이스케이프)로 시작한다. 데이터가 수백~수천 건 규모라 인덱스 없이 충분하고, 느려지면 **pg_trgm(trigram) 인덱스**를 추가한다(쿼리 변경 없이 인덱스만). 장소명(name) 검색 확장은 `OR name ILIKE` 한 줄이면 된다.
- **필터 상태는 클라이언트 소유**다. 카테고리(기초 주행 등)는 연습유형을 묶어 보여주는 **클라 전용 UX 개념**이고, 온보딩 기본값 계산·로컬 저장·변경 유지·카테고리→연습유형 변환 모두 클라가 한다. 클라는 선택을 **기존 `PracticeType` 리스트로 풀어** `practiceTypes` 파라미터(콤마 구분)로 보내고, 서버는 검증·매칭·**정렬만** 한다. 서버 DB 저장도, 서버 측 카테고리 enum도 없다.
  - 레벨 산정·추천 태그를 클라가 소유하는 기존 방침([스펙 004](../specs/004-onboarding.md))과 일관된다.
  - 혼합 카테고리 선택은 연습유형 합집합이라 서버는 카테고리 경계를 알 필요가 없다.
- **정렬은 "필터 매칭 우선 → 현위치 거리 → id"** 3-키이며, 필터는 필터링이 아니라 정렬이다(비매칭도 후순위로 전부 노출). 커서 keyset을 `(matched, distance, id)`로 확장한다 — [ADR 0010](0010-list-query-cursor-postgis.md)의 커서 패턴에 정렬 키만 추가.

## 결과

### 긍정적

- 로그인 여부와 무관하게 **필터 동작이 단일 경로**(항상 파라미터) — 클라 분기·동기화 코드 없음, 비로그인 필터도 자연 지원.
- 서버 구현 최소화: DB 마이그레이션·필터 저장 API·인증 변경 전부 불필요. 검색 쿼리도 기존 native query 패턴 재사용.
- 기존 뷰포트 목록 API는 `practiceTypes` 미전달 시 완전히 기존과 동일(하위 호환).
- 서버 측 신규 enum·개념이 없다 — 기존 `PracticeType`·태그 테이블만으로 매칭.

### 부정적

- 재설치·기기 변경 시 필터 상태가 초기화된다(클라가 서버의 레벨로 기본값 재계산해 부분 복구). 기기 간 동기화가 필요해지면 서버 저장을 재검토해야 한다.
- `%kw%` 패턴은 인덱스를 못 타므로 데이터가 커지면 pg_trgm 도입 시점을 챙겨야 한다.

### 중립적

- 검색·목록 두 엔드포인트가 정렬·커서 로직을 공유하므로 쿼리 구성은 공통화가 필요하다.
- `PARKING` 연습유형이 두 카테고리(도심 기본·넓은 공간)에 겹치지만, 전송 값이 합집합이고 칩 상태의 진실은 클라 로컬이라 서버엔 영향이 없다.

## 검토한 대안

### 대안 1 — 기존 목록 API에 keyword 파라미터 추가

엔드포인트 1개 유지가 장점이나, bbox·현위치 필수인 기존 검증을 조건부로 바꿔야 하고 "뷰포트 모드/검색 모드"가 한 API에 섞여 커서 의미까지 분기된다. 검증된 API를 건드리는 회귀 리스크도 있어 배제.

### 대안 2 — PostgreSQL full-text search·외부 검색엔진(Elasticsearch 등)

형태소·관련도 랭킹이 강점이나, 시군구 주소 부분일치라는 요구에는 과하다. 운영 부담(별도 인프라·색인 동기화) 대비 이득이 없어 배제. 자동완성·장소명 유사 검색이 커지면 재검토.

### 대안 3 — 필터 서버 저장 (member.filter_tags 컬럼 + PUT API + 옵셔널 JWT)

재설치·기기 변경에도 필터가 유지되는 장점. 그러나 비로그인 필터 요구로 클라가 로컬 저장+파라미터 경로를 어차피 구현해야 해서, 서버 저장을 얹으면 필터 상태의 진실이 두 곳(로컬/서버)이 되고 병합·동기화 규칙이 필요해진다. 스펙 리뷰에서 채택했다가 이 이유로 **철회**했다.

### 대안 4 — 서버 측 카테고리 enum(FilterCategory 5종)

카테고리를 서버 enum으로 두고 파라미터·검증·연습유형 확장을 서버가 담당하는 안. 선택 상태 복원 모호성(PARKING이 두 카테고리에 겹침) 때문에 서버 저장(대안 3) 전제에선 필요했으나, 클라 로컬 저장으로 확정되며 복원 자체가 서버 일이 아니게 됐다. 카테고리는 사용자 이해를 돕는 UX 그룹핑일 뿐이고 혼합 선택은 합집합이라, 서버는 기존 `PracticeType`만 알면 충분해 **배제**했다.
