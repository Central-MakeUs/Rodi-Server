# ADR 0012: 방문 기록 중복 방지 — 쿨다운

## 상태 (Status)

Accepted (2026-08-09)

## 배경

연습 코스 방문 기록(`POST /api/v1/practices/{id}/visits`)은 사용자가 버튼을 누르는 게 아니라 **앱이 이동 추적 결과로 자동 호출**한다. 그래서 서버 입장에서 한 번의 실제 방문이 여러 요청으로 들어올 수 있다 — 네트워크 재시도, 앱 재시작 후 재전송, 추적 로직의 중복 발화.

이 호출은 **비멱등**이다. 부를 때마다 `visit_count`가 오르고 인정 주행거리가 누적된다.

지금까지는 피해가 크지 않았다. 중복 호출이 연습 횟수를 부풀릴 뿐이고, 인증 여부는 필요 거리(`min(코스거리 × 40%, 5km)`) 도달만 보므로 여러 번 불려도 결과가 같았다.

**스펙 012(누적 주행거리 기반 레벨 승급)가 그 균형을 깼다.** 이제 같은 값이 회원의 누적 주행거리로 환산되고, 기준에 도달하면 레벨이 오른다. 그리고 **레벨은 어떤 경우에도 내려가지 않고 거리도 차감하지 않는다** — 잘못 오른 레벨을 되돌릴 경로가 없다. 재시도 한 번이 영구적인 부당 이득이 된다.

스펙 011·012 작성 시점에는 "중복 호출 가드는 두지 않는다. 문제가 관측되면 쿨다운이나 멱등키를 추가한다"로 결정했으나, 012 착수 시 재판단하기로 남겨 두었다. 이 ADR이 그 재판단이다.

## 결정

**직전 방문 후 10분 안에 같은 연습 항목으로 들어온 방문 기록 호출은 같은 방문으로 보고 무시한다.**

- 판정 기준은 이미 저장하고 있는 `member_practice.visited_at`이다. 새 컬럼·테이블이 없다.
- **연습 항목 행을 잠그고 판정한다.** 잠금이 없으면 동시에 도착한 두 요청이 서로의 미커밋 `visited_at`을 못 봐 둘 다 통과한다. 잠금 순서는 항상 **연습 항목 → 회원**이다(회원 행은 누적 갱신 때문에 원래 잠근다).
- 무시한 요청에는 **200과 현재 상태**를 돌려준다. 오류(409)로 주면 앱이 실패로 보고 다시 시도해 문제가 반복된다. 이번 회차로 반영된 게 없으므로 `addedCertifiedDistanceMeters`는 0, `isCertifiedNow`·`levelUp`은 false이고, `isVerified`·`visitCount`·`totalDistanceKm`은 사실 그대로 내려간다.
- **클라이언트 변경이 없다.** 요청 형식도 응답 형식도 그대로다.

이 결정은 [스펙 012의 누적 상한](../specs/012-level-progress.md)(한 방문에 쌓이는 거리를 `min(측정값, 코스 전체 거리)`로 자름)과 **함께 작동한다**. 상한은 한 번의 호출이 만들 수 있는 최대 피해를 묶고, 쿨다운은 호출 자체의 횟수를 줄인다.

## 결과

### 긍정적

- 재시도·연타로 인한 중복 누적이 실질적으로 사라진다. 같은 코스를 10분 안에 두 번 완주하는 경우는 현실적으로 없다.
- 서버만 고치면 된다 — 앱 배포를 기다리지 않고 지금 막을 수 있다.
- 저장 구조가 늘지 않는다. 판정에 쓰는 `visited_at`은 원래 있던 컬럼이다.
- 연습 횟수(`visit_count`)의 신뢰도도 함께 올라간다. 레벨과 무관하게 화면에 노출되는 값이다.
- 행 잠금 덕에 **동시에 도착한 요청도 걸러진다.** 늦게 잠근 쪽은 앞선 방문이 커밋된 뒤 읽으므로 쿨다운에 걸린다.

### 부정적

- **정확한 중복 제거가 아니다.** 서로 다른 두 방문이 10분 안에 일어나면 뒤엣것이 버려진다. 짧은 코스(최소 1.3km)를 연속으로 두 바퀴 도는 경우가 이에 해당하며, 사용자는 두 번째가 반영되지 않은 것을 알 방법이 없다(응답이 성공이라).
- 10분이라는 값에 근거가 약하다. 관측 데이터가 아니라 판단으로 정했다.

### 중립적

- 쿨다운 시간은 `MemberPractice.VISIT_COOLDOWN_MINUTES` 한 곳에 있다. 조정에 마이그레이션이 필요 없다.
- 한 회원의 방문 기록은 원래 직렬이라, 행 잠금으로 인한 대기가 실사용에서 관측될 일은 없다.
- 무시된 호출을 로그·지표로 남기지 않았다. 실제 중복 빈도를 알고 싶어지면 그때 계측을 붙인다.

## 검토한 대안

### 가드를 두지 않는다 (기존 결정 유지)

누적 상한이 이미 들어가 한 번의 중복으로 뛸 수 있는 폭이 코스 거리만큼으로 묶였으니, 관측될 때까지 두자는 안.

되돌릴 수 없다는 점 때문에 택하지 않았다. 레벨이 내려가지 않고 거리도 차감하지 않으므로, "관측되면 고친다"는 그때까지 부당하게 오른 레벨을 그대로 안고 간다는 뜻이다. 40km 코스라면 재시도 한 번이 40km다.

### 멱등키 (`Idempotency-Key` 또는 `visitId`)

앱이 방문마다 고유 키를 만들어 보내고 서버가 키별로 한 번만 반영하는 안. 가장 정확하다 — 진짜 두 번째 방문과 재전송을 구분할 수 있다.

**클라이언트 변경이 필요하고**, 키를 저장할 테이블과 만료 정책이 따라온다. 지금 필요한 건 재시도 흡수이고 그건 쿨다운으로 충분하다. 짧은 코스 연속 주행이 실제로 문제가 되거나 중복 빈도가 높게 관측되면 이쪽으로 옮긴다.

### 요청 본문에 방문 시각을 받아 판정

앱이 측정 세션의 종료 시각을 보내고 서버가 같은 시각의 중복을 거르는 안. 클라이언트 변경이 필요한 데다 **시각을 앱이 준다** — 조작하면 그대로 뚫린다. 서버가 아는 값(`visited_at`)으로 판정하는 편이 낫다.
