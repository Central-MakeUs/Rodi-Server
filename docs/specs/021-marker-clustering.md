## 배경 / 목적

지도는 장소를 숫자 원으로 묶어 보여주고, 확대하면 개별 장소를 보여준다. 지금은 `GET /places/coordinates`가 장소 전체 좌표를 주고 앱이 각자 묶는다. iOS·안드로이드가 **같은 규칙으로 같은 결과**를 보여주도록 클러스터링을 서버로 옮긴다.

화면 흐름은 다음과 같다.

| 사용자 동작 | 일어나는 일 |
|-------------|-------------|
| 처음 진입 / "재검색" 버튼 | 그때의 화면 범위로 **검색**. 지도 마커(묶음)와 아래 추천 목록이 그 범위의 장소로 채워진다 |
| 확대·축소 | 새 검색 없이 **같은 장소들의 묶음만** 바뀐다 |
| 카메라 이동 | 아무 일도 없다. 검색 결과는 그대로다 |
| 클러스터 탭 | 그 클러스터의 범위로 확대되며 묶음이 풀린다 |

그래서 **검색할 때 서버가 확대 단계별 묶음을 모두 계산해 한 번에** 주고, 확대·축소할 때 앱은 서버에 묻지 않고 받아 둔 단계 중 하나를 골라 그린다. 방식은 **고정 그리드**다. 선택 이유와 대안은 [ADR 0015](../adr/0015-server-side-grid-marker-clustering.md)에 정리했다.

### 범위 밖

- 거리 기반 클러스터링 — 추후 검토(ADR 0015의 전환 조건).
- 클러스터 탭 시 묶인 장소 목록 조회 — 디자인에 없다.
- 추천 목록(`GET /places`) 변경 — 그대로 쓴다. 검색할 때 앱이 같은 범위로 함께 부른다.
- `GET /places/coordinates` 제거 — 앱 전환 후 별도 작업.

## 요구사항

### 기능 요구사항

1. **검색**: 검색 범위(화면 bbox)를 받아, 그 범위의 장소 목록과 **확대 단계별 묶음**을 준다.
2. **묶는 대상**: 검색 범위 안의 장소만 — 주차장 전체 + 승인(`APPROVED`)·미삭제 코스, 여기에 회원 유형 필터(#74와 같은 규칙: 인증 회원이 필터를 가지면 맞는 장소만, 비로그인·빈 필터는 전부).
3. **목록과 개수 일치**: 어느 단계든 `클러스터 개수 합 + 개별 장소 수 = 장소 목록 수`이고, 같은 범위·같은 필터의 `GET /places` 전체 개수(`totalCount`)와 같다.
4. **고정 그리드**: Web Mercator(EPSG:3857) 원점에 고정된 정사각형 격자로 나눈다. 같은 칸의 장소가 **2개 이상이면 클러스터, 1개면 개별 장소**다.
5. **단계**: 단계마다 칸 크기가 정해져 있고(2배 단위), 단계마다 **쓰이는 화면 경도 폭 범위**(`minLngSpan` 이상 `maxLngSpan` 미만)를 붙인다. 앱은 지금 화면의 경도 폭으로 단계를 고른다([단계 구성](#단계-구성)).
6. **묶지 않는 단계**: 화면 폭이 지상 약 1km 이하인 범위에서는 모든 장소를 개별로 보여주는 단계를 쓴다.
7. **가장 넓은 단계 = 한반도 전체 화면**: 앱은 최대 축소를 한반도 전체가 보이는 정도로 제한한다. 그 화면에서 전국을 검색하면 마커가 **약 6~8개**(팔도 정도의 밀도)가 되도록 가장 넓은 단계의 칸 크기를 정한다(튜닝 목표).
8. **클러스터 정보**: 개수, 위치, 범위(`bounds`, 묶인 장소들을 감싸는 영역). 앱은 탭하면 `bounds`에 맞춰 카메라를 옮긴다.
9. **클러스터 위치는 칸 안쪽으로 제한한 중심점**: 묶인 장소들의 중심점에 그리되, 칸 가장자리에서 칸 크기의 1/4 안쪽 영역을 벗어나면 그 영역 안으로 당긴다([클러스터 위치](#클러스터-위치)).
10. **`bounds` 최소 크기**: 탭 한 번에 반드시 개별 장소로 풀리도록 `bounds`의 가로·세로를 최소 크기 이상으로 넓힌다([bounds 최소 크기](#bounds-최소-크기)).
11. **결정적 응답**: 같은 범위·같은 필터면 항상 같은 응답(항목·순서)을 준다.

### 비기능 요구사항

- **공개 API + 옵셔널 JWT**(필터 적용용). `SecurityConfig` 공개 경로에 추가하고 `@CurrentMember(required = false)`로 받는다 — #74의 `/places/coordinates`와 같은 방식.
- **조회 1회 + 메모리 계산**: 검색 범위의 장소를 bbox 인덱스(`idx_place_location`, GiST)로 한 번 조회하고, 단계별 묶음은 애플리케이션에서 계산한다. 합성 장소 1만 개 기준 응답 시간을 측정해 구현 노트에 기록한다(CI 단언은 하지 않는다).
- **알고리즘과 무관한 응답**: 칸 번호·칸 크기 등 그리드 전용 값을 응답에 넣지 않는다(ADR 0015 §5).
- **기본값은 설정으로**: 칸 수·묶지 않는 폭·원 위치 제한을 `application.yml` 설정값으로 두어 코드 수정 없이 조정한다.

### `GET /api/v1/places/clusters`

```
GET /api/v1/places/clusters?swLat=37.45&swLng=126.80&neLat=37.65&neLng=127.15
```

| 파라미터 | 필수 | 설명 |
|----------|------|------|
| `swLat`·`swLng` | O | 검색 범위(검색 시점 화면) 남서 모서리 |
| `neLat`·`neLng` | O | 검색 범위 북동 모서리 |

- 위도 −85~85(Web Mercator 유효 범위), 경도 −180~180, `swLat < neLat`, `swLng < neLng`가 아니면 400 `COMMON_400`. 날짜변경선을 넘는 범위는 지원하지 않는다(국내 서비스).

```json
{
  "isSuccess": true, "code": "COMMON_200", "message": "요청에 성공했습니다.",
  "data": {
    "places": [
      { "id": 12, "type": "PARKING", "name": "여의도 공영주차장", "address": "서울특별시 영등포구", "lat": 37.528, "lng": 126.932 },
      { "id": 40, "type": "COURSE", "name": "망원한강공원", "address": "서울특별시 마포구", "lat": 37.555, "lng": 126.896 }
    ],
    "levels": [
      {
        "minLngSpan": 4.1630, "maxLngSpan": null,
        "clusters": [
          { "lat": 37.541, "lng": 126.914, "count": 2,
            "bounds": { "swLat": 37.528, "swLng": 126.896, "neLat": 37.555, "neLng": 126.932 } }
        ],
        "placeIds": []
      },
      {
        "minLngSpan": 0, "maxLngSpan": 0.0112,
        "clusters": [],
        "placeIds": [12, 40]
      }
    ]
  }
}
```

| 필드 | 설명 |
|------|------|
| `places` | 검색 범위의 장소 전체(필터 적용). 기존 `PlaceCoordinateResponse`와 같은 필드. id 오름차순 |
| `levels` | 확대 단계. **넓은 화면용 → 좁은 화면용** 순서(그리드 단계들 → 묶지 않는 단계). 예시는 일부 단계만 보였다 |
| `levels[].minLngSpan`·`maxLngSpan` | 이 단계를 쓰는 화면 경도 폭 범위(`min` 이상 `max` 미만). `maxLngSpan: null`은 상한 없음(가장 넓은 단계) |
| `levels[].clusters` | 클러스터. `lat`·`lng`는 그릴 위치, `count`는 묶인 장소 수(2 이상), `bounds`는 탭했을 때 맞출 범위 |
| `levels[].placeIds` | 이 단계에서 개별로 그릴 장소 id(`places`에서 찾는다). 오름차순 |

- 장소 정보는 `places`에 한 번만 담고 단계에서는 id로 참조한다. 단계마다 같은 장소 정보를 반복하지 않기 위해서다.
- 단계의 경도 폭 범위는 빈틈없이 이어지고 겹치지 않는다. 가장 좁은 단계는 `minLngSpan: 0`이다.
- 클러스터 순서: 위도 내림차순 → 경도 오름차순(결정적 응답용, 그리는 순서에는 의미 없음).
- 검색 범위에 장소가 없으면 `places: []`, 단계마다 `clusters: []`·`placeIds: []`다.

## 도메인 모델

스키마 변경 없음. `place.location`(geometry(Point, **SRID 4326**))과 기존 GiST 인덱스로 검색 범위의 장소를 조회한다. 칸 계산은 애플리케이션에서 Web Mercator(**EPSG:3857**) 좌표로 한다.

```
X = R · λ            Y = R · ln(tan(π/4 + φ/2))        (R = 6,378,137, λ·φ는 라디안)
```

경도 1도는 X로 `R·π/180 ≈ 111,319.49`다. X가 경도에 정비례하므로 **화면 X 폭 = 경도 폭 × 111,319.49**이고, 앱은 경도 폭만으로 단계를 고를 수 있다.

### 설정값

`application.yml`의 `marker-cluster.*`로 둔다. 화면을 보며 조정한다([튜닝](#기본값-튜닝)).

| 설정 | 기본값 | 의미 |
|------|--------|------|
| `target-columns` | 5 | 화면 가로에 들어갈 목표 칸 수 |
| `no-cluster-width` | 1,250 (3857 단위) | 화면 폭이 이 이하면 묶지 않는다. 한국 위도에서 지상 약 1km |
| `max-cell-level` | 17 | 가장 넓은 단계의 칸 크기 지수(`2^17` = 131,072, 지상 약 105km). 한반도 전체 화면용 |
| `cluster-inset-ratio` | 0.25 | 클러스터 위치를 칸 가장자리에서 칸 크기의 이 비율만큼 안쪽으로 제한 |

`bounds` 최소 크기는 `no-cluster-width / 2`로 계산한다(따로 설정하지 않는다).

### 단계 구성

단계 `k`의 칸 크기는 `cell = 2^k`(3857 단위)다. 화면 X 폭 `W`에 맞는 단계는 **`round(log2(W / target-columns)) = k`** 인 단계, 즉

```
W ∈ [ target-columns · 2^k / √2 ,  target-columns · 2^k · √2 )
```

이고, 이 범위를 111,319.49로 나눠 경도 폭(`minLngSpan`·`maxLngSpan`)으로 준다. 화면에는 약 3.5~7칸이 들어간다.

**어떤 단계를 담나** — 검색 범위·장소 분포와 무관하게 **항상 같은 구성**이다(넓은 순).

1. **가장 넓은 단계** `k = max-cell-level`(기본 17, 칸 131,072 ≈ 지상 약 105km). 범위 상한은 `null`이라, 이보다 넓은 화면에서도 이 단계를 쓴다. 앱이 최대 축소를 한반도 전체로 제한하므로 실제로는 **한반도 전체 화면용** 단계다.
2. 그 아래로 한 단계씩(칸 절반씩) 내려가며, 범위 상한이 `no-cluster-width`보다 큰 가장 작은 `k`까지 담는다(기본 `k = 8`). 그 단계의 하한은 `no-cluster-width`로 자른다.
3. **묶지 않는 단계**: `[0, no-cluster-width)`, 모든 장소를 `placeIds`로.

기본값이면 그리드 단계 17~8(10개) + 묶지 않는 단계 = **11단계**다.

**한반도 전체 화면의 마커 수(튜닝 목표 6~8개)** — 세로 화면에 한반도 전체가 들어오면 화면 가로가 경도 약 5.4°(X 약 600,000)다. 기본값이면 `round(log2(600,000 / 5)) = 17` 단계(칸 지상 약 105km)를 쓰고, 남한에 칸이 10개 남짓 걸친다. 장소가 전국에 고루 있으면 8개를 넘을 수 있고, 수도권에 몰려 있으면 더 적다. 그래서 **실제 장소 데이터로 그려 보며** `max-cell-level`(가장 넓은 칸 크기)과 `target-columns`를 맞춘다. 디자인 시안의 시내 화면에 클러스터가 3개인 점도 `target-columns`를 5보다 줄일 여지가 있다는 신호다.

### 묶는 절차 (단계마다)

1. 장소마다 칸 번호 `(floor(X / cell), floor(Y / cell))`를 구해 묶는다.
2. 칸에 장소가 1개면 `placeIds`에, 2개 이상이면 클러스터로.
3. 클러스터 중심점 = 묶인 장소 X·Y의 평균. 위치 제한(아래)을 적용한 뒤 위경도로 되돌린다.
4. `bounds` = 묶인 장소 위경도의 최솟값·최댓값. 최소 크기(아래)를 적용한다.

### 클러스터 위치

중심점을 그대로 쓰면, 이웃한 두 칸의 장소가 모두 공유 경계 근처에 몰려 있을 때 두 원이 경계에 붙어 겹친다. 칸 중앙에 그리면 겹치지 않지만, 장소가 칸 구석에 있어도 가운데에 떠 위치가 부정확해진다(시내 화면 기준 최대 약 2km).

그래서 **중심점을 칸 안쪽 영역으로 제한**한다(3857 좌표 기준).

```
inner = cell · cluster-inset-ratio
x = clamp(중심점X, 칸최소X + inner, 칸최대X − inner)
y = clamp(중심점Y, 칸최소Y + inner, 칸최대Y − inner)
```

- 이웃한 두 클러스터 원은 **최소 칸 크기의 절반만큼 떨어진다.** 칸이 화면 가로의 약 1/5이므로, 폰 화면(가로 약 375pt)에서 최소 간격은 약 37pt다.
- 중심점이 이미 안쪽 영역에 있으면(대부분) 그대로다.
- 탭 동작은 영향받지 않는다. 카메라 이동은 원 위치가 아니라 `bounds`(실제 장소 범위)로 정한다.

### `bounds` 최소 크기

여러 장소가 거의 같은 좌표에 있으면 `bounds`가 점처럼 작아진다. 앱이 그 범위에 맞추면 SDK의 최대 확대까지 가도 같은 칸에 들어가 풀리지 않을 수 있다.

`bounds`의 가로·세로(3857 기준)가 `no-cluster-width / 2`보다 작으면 중심(묶인 장소 범위의 중앙) 기준으로 그 크기까지 넓힌다. 범위에 맞춘 화면 폭이 앱 여백(padding)을 더해도 `no-cluster-width` 이하가 되어, 앱이 **묶지 않는 단계**를 고르게 된다. 즉 **탭 한 번에 반드시 개별 장소로 풀린다.**

### 구성요소 (`domain/place`)

| 구성요소 | 역할 |
|----------|------|
| `MarkerClusterRequest` | 검색 범위 4개 + 검증 |
| `MarkerClusterResponse` | `places` + `levels` |
| `MarkerClusterProperties` | `marker-cluster.*` 설정 바인딩 |
| `MarkerClusterer` | 투영·단계 구성·칸 묶기·위치 제한·`bounds` 최소 크기(순수 계산, 단위 테스트 대상) |
| `PlaceRepository` | 검색 범위 장소 조회(노출 조건·필터 포함) |
| `PlaceQueryService.getClusters` | 필터 해석(#74의 `resolveFilter`) → 조회 → `MarkerClusterer` → 응답 |

## 앱 연동 가이드

| 상황 | 앱 동작 |
|------|---------|
| 처음 진입 / 재검색 | 지금 화면 범위로 `GET /places/clusters`와 `GET /places`(추천 목록)를 함께 부른다 |
| 축소 한도 | 지도 SDK의 최소 레벨을 **한반도 전체가 보이는 정도**로 제한한다 |
| 확대·축소 | **서버에 요청하지 않는다.** 지금 화면의 경도 폭(`동쪽 경도 − 서쪽 경도`)이 `minLngSpan` 이상 `maxLngSpan` 미만(`null`은 무한대)인 단계를 골라 그 단계의 `clusters`와 `placeIds`를 그린다 |
| 카메라 이동 | 아무것도 하지 않는다. 받아 둔 결과를 그대로 그린다 |
| 클러스터 탭 | `bounds`를 SDK 범위 맞춤(카카오 `CameraUpdate.fitMapPoints` 등)에 넘긴다. 여백(padding)은 앱이 정한다. 확대가 끝나면 위 규칙대로 단계를 다시 고른다 |
| 마이그레이션 | `/places/clusters`로 옮긴 뒤 `/places/coordinates` 호출을 없앤다. 서버는 그 뒤 제거한다 |

## 기본값 튜닝

기본값(5칸·1km·1/4·가장 넓은 칸 2^17)으로 시작하고, **로컬 전용 튜닝 페이지**에서 실제 지도에 그려 보며 조정한다. 확인할 기준은 두 가지다.

- 시내 화면의 클러스터 수가 디자인 시안(시내 화면에 3개 안팎)과 비슷한가.
- 한반도 전체 화면에서 전국을 검색했을 때 마커가 약 6~8개인가.

### 튜닝 페이지

| 항목 | 내용 |
|------|------|
| 위치 | `GET /dev/cluster-tuning` — **`local` 프로필에서만** 등록되는 컨트롤러가 페이지를 준다. 다른 프로필(운영 포함)에서는 등록되지 않아 404다 |
| 코드 | 운영 코드와 분리된 **별도 소스 폴더 `src/dev`**(`src/dev/java/cmc/rodi/dev/…`, `src/dev/resources/dev/…`). git으로 관리한다. Gradle `dev` 소스셋으로 **`bootRun`(로컬 실행)에만 포함**하고 배포용 `bootJar`·운영 이미지에는 넣지 않는다. 운영 코드가 바뀌어 튜닝 코드가 깨지는 것을 알 수 있도록 `./gradlew build`(CI)는 `dev` 소스셋도 컴파일한다 |
| Swagger | 튜닝 컨트롤러는 `@Hidden`으로 API 문서에 노출하지 않는다(로컬 Swagger에도 안 보임) |
| 지도 | Leaflet + OpenStreetMap 타일(키 불필요, Web Mercator). 앱의 카카오 지도와 투영·글꼴·원 크기가 조금 다를 수 있어, 튜닝 후 최종 모습은 앱 연동 때 한 번 더 확인한다 |
| 데이터 | 로컬 DB의 장소. 노출 조건은 실제 API와 같다(필터는 비로그인 기준 — 전부) |
| 계산 | 실제 서버 코드(`MarkerClusterer`)를 그대로 쓴다. 페이지가 바꾼 설정값만 요청에 실어 보내는 **튜닝 전용 엔드포인트**(`GET /dev/places/clusters`, `local` 전용)를 거친다. 운영 API `/places/clusters`는 설정 덮어쓰기를 받지 않는다 |
| 조작 | 슬라이더로 `target-columns`·`no-cluster-width`·`cluster-inset-ratio`·`max-cell-level`을 바꾸면 바로 다시 계산해 그린다 |
| 화면 크기 | 폰 화면 틀(예: 375×812, 393×852)을 골라 그 크기의 지도 영역에서 본다 |
| 앱 흐름 재현 | "재검색" 버튼으로 검색, 확대·축소는 요청 없이 단계만 전환(앱 규칙 그대로), 클러스터 클릭 시 `bounds`로 이동. 화면에 현재 경도 폭·단계·마커 수를 표시 |
| 결과 반영 | 화면에서 정한 값을 `application.yml`의 `marker-cluster.*` 기본값으로 옮겨 커밋한다 |

## 완료 조건 (Acceptance Criteria)

**단계 구성**

- [ ] 기본값에서 단계는 넓은 순으로 그리드 17~8과 묶지 않는 단계, 모두 11개이고, 검색 범위가 달라도 단계 구성(개수·경도 폭 범위)이 같다.
- [ ] 가장 넓은 단계는 `maxLngSpan: null`이다.
- [ ] 단계의 경도 폭 범위가 빈틈·겹침 없이 이어지고, 가장 넓은 단계는 `maxLngSpan: null`, 가장 좁은 단계는 `minLngSpan: 0`이다.
- [ ] 묶지 않는 단계의 `maxLngSpan`은 `no-cluster-width / 111,319.49`이고, `placeIds`에 모든 장소가 있다.

**묶기**

- [ ] 같은 칸에 장소 3개, 다른 칸에 1개가 있으면 그 단계에 클러스터(count 3) 1개와 `placeIds` 1개가 있다.
- [ ] 모든 단계에서 `클러스터 count 합 + placeIds 수 = places 수`다.
- [ ] `places` 수가 같은 범위·같은 필터의 `GET /places` `totalCount`와 같다.
- [ ] 검색 범위 밖의 장소는 어느 단계에도 없다.
- [ ] 클러스터 `lat`·`lng`는 묶인 장소들의 중심점이고(칸 안쪽 영역에 있을 때), `bounds`는 묶인 장소들을 모두 포함한다.
- [ ] 중심점이 칸 가장자리 1/4 영역에 있으면 클러스터 위치가 안쪽 영역 경계로 당겨진다 — 공유 경계에 장소가 몰린 이웃 두 칸의 클러스터 위치가 칸 크기의 절반 이상 떨어진다.
- [ ] 같은 좌표의 장소 2개로 만든 클러스터의 `bounds`는 가로·세로가 `no-cluster-width / 2` 이상이고, 그 `bounds`의 경도 폭은 묶지 않는 단계 범위 안에 든다.
- [ ] 같은 지역을 서로 다른(겹치는) 범위로 검색해도, 두 범위 모두에 완전히 들어가는 칸의 클러스터는 같은 단계에서 같다(격자 고정).
- [ ] 같은 요청을 두 번 보내면 응답이 같다.

**노출·필터**

- [ ] 미승인(`PENDING`·`REJECTED`)·삭제된 코스는 `places`와 어느 단계에도 없다.
- [ ] 필터가 있는 인증 회원에게는 필터에 맞는 장소만 준다(코스는 태그 겹침, 주차장은 PARKING 포함 시). 비로그인·빈 필터는 전부다.
