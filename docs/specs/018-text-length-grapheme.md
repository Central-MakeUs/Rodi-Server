## 배경 / 목적

프론트에서 다음 리포트가 올라왔다.

> 안드로이드와 iOS의 이모지 글자 처리 방식이 달라, 안드로이드에서 이모지를 30자로 처리해 전달해도 서버가 15자만 받는다. 서버에서 UTF-16 문자열 단위로 제한하면 안드로이드는 정상 처리할 수 없다. 서버 처리가 힘들다면 이모지 자체를 입력하지 못하도록 막아야 한다.

원인은 **서버·클라이언트가 "1자"를 서로 다른 단위로 세는 것**이다. 현재 운전 목표에는 길이 제한이 두 겹 걸려 있는데, 그 둘도 단위가 다르다.

| 위치 | 현재 | 세는 단위 |
|------|------|-----------|
| 요청 검증 | `@Size(max = 30)` | **UTF-16 code unit** (`String.length()`) |
| DB 컬럼 | `driving_goal VARCHAR(30)` | **코드포인트** (Postgres varchar는 문자 수) |
| iOS | `String.count` | **grapheme cluster** |
| 안드로이드 | `BreakIterator` 사용 시 | **grapheme cluster** |

`@Size`가 가장 빡빡해 DB에 닿기 전에 거절되므로 지금 DB 에러는 나지 않지만, 사용자가 화면에서 세는 수와 서버가 세는 수가 어긋난다.

| 입력 | UTF-16 | 코드포인트 | grapheme | 현재 한도(30)로 입력 가능한 개수 |
|------|--------|-----------|----------|--------------------------------|
| `가` | 1 | 1 | 1 | 30개 |
| 😀 | 2 | 1 | 1 | **15개** |
| ❤️ (변이선택자) | 2 | 2 | 1 | 15개 |
| 👍🏻 (피부톤) | 4 | 2 | 1 | **7개** |
| 👨‍👩‍👧‍👦 (ZWJ 가족) | 11 | 7 | 1 | **2개** |

**사용자가 보는 글자 수 = grapheme cluster**이므로, 서버도 grapheme으로 세도록 바꾼다. 그러면 iOS·안드로이드·서버 셋이 같은 수를 세게 된다.

프론트가 대안으로 제시한 **이모지 입력 차단은 채택하지 않는다.** "이모지"를 정확히 판별하는 규칙(변이선택자·ZWJ·국기·피부톤)이 까다로워 오탐이 생기고, 운전 목표·후기에 이모지를 쓰는 건 자연스러운 사용이라 UX 손해가 크다.

### 함께 정정할 오해

서버는 초과분을 **자르지 않는다.** 한도를 넘으면 `400 COMMON_400`으로 요청 전체를 거절한다(`GlobalExceptionHandler`의 `MethodArgumentNotValidException` 처리). "15자만 받고 자른다"는 리포트는 16번째 이모지부터 400이 나 저장이 안 된 것을 잘림으로 해석한 것으로 보인다. 이 동작(거절)은 이번 변경에서도 유지한다.

### 범위 밖

- **다른 텍스트 필드** — 후기 주의사항(제한 없음), 신고 상세·미방문 사유 직접입력(100), 최근검색 표시명(100), 코스명(255)·설명·주의사항. 같은 문제를 갖고 있지만 이번에는 **QA에서 실제로 걸린 두 필드만** 바꾼다. 새 애노테이션은 재사용 가능하게 만들어 두므로 이후 필드는 한 줄 교체로 확장한다.
- **클라이언트의 글자 수 카운터 구현** — 앱이 `BreakIterator`(안드로이드) / `String.count`(iOS)로 세도록 맞추는 건 앱 몫이다.
- **이모지 차단·필터링**.
- **초과 시 서버 truncate** — 잘라 저장하지 않는다(입력 단계에서 앱이 막는다).

## 요구사항

### 기능 요구사항

1. **grapheme 기준 검증**: 운전 목표(30)·후기 내용(150)의 길이를 **grapheme cluster 수**로 센다. 이모지 30개짜리 운전 목표는 종류와 무관하게 통과해야 한다.
2. **한도 초과는 거절**: 한도를 넘으면 저장하지 않고 `400 COMMON_400`으로 응답한다. 잘라서 저장하지 않는다.
3. **저장 실패 없음**: 검증을 통과한 값은 **반드시 DB에 저장된다.** grapheme 30자는 코드포인트로 210자(가족 이모지 30개)를 넘길 수 있어 현재 컬럼 폭으로는 들어가지 않는다 → 컬럼을 넓힌다.
4. **재사용 가능한 검증**: 다른 텍스트 필드도 애노테이션 한 줄로 같은 규칙을 적용할 수 있어야 한다.
5. **기존 데이터 유지**: 이미 저장된 값은 그대로 남는다. 현재 검증이 새 기준보다 빡빡했으므로 새 기준을 어기는 기존 데이터는 존재할 수 없다.

### 비기능 요구사항

- **저장 크기 상한**: grapheme cluster는 이론상 길이 제한이 없다(ZWJ·결합문자를 무한히 이을 수 있다). 컬럼을 `TEXT`로 여는 대신 **코드유닛 절대 상한을 함께 둔다** — `grapheme ≤ max` **AND** `UTF-16 code unit ≤ max × 20`. 정상 입력(가족 이모지 11 code unit)은 여유롭게 통과하고, 비정상적으로 부풀린 값만 막는다.
- 검증 실패 응답 형식은 기존 Bean Validation 응답과 동일하게 유지한다(필드명 → 메시지 맵).
- 인증 요구사항은 기존 엔드포인트와 동일(모두 JWT).

## API 명세

**엔드포인트·요청·응답 스키마 변경 없음.** 통과/거절 기준만 바뀐다.

| Method | Path | 대상 필드 | 한도 | 인증 |
|--------|------|-----------|------|------|
| PATCH | `/api/v1/members/me` | `drivingGoal` | 30 grapheme | JWT |
| POST | `/api/v1/members/me/onboarding` | `drivingGoal` | 30 grapheme | JWT |
| POST | `/api/v1/places/{placeId}/reviews` | `content` | 150 grapheme | JWT |
| PUT | `/api/v1/reviews/{reviewId}` | `content` | 150 grapheme | JWT |

변경 전후 동작 비교 (운전 목표에 😀 20개 = grapheme 20 / UTF-16 40):

```json
// Request  PATCH /api/v1/members/me
{ "drivingGoal": "😀😀😀😀😀😀😀😀😀😀😀😀😀😀😀😀😀😀😀😀" }

// 변경 전 Response (400)
{
  "isSuccess": false,
  "code": "COMMON_400",
  "message": "입력값이 올바르지 않습니다.",
  "data": { "drivingGoal": "크기가 0에서 30 사이여야 합니다" }
}

// 변경 후 Response (200)
{ "isSuccess": true, "code": "COMMON_200", "message": "요청에 성공했습니다.", "data": null }
```

한도 초과 시 응답(운전 목표 31 grapheme):

```json
{
  "isSuccess": false,
  "code": "COMMON_400",
  "message": "입력값이 올바르지 않습니다.",
  "data": { "drivingGoal": "30자 이하로 입력해주세요." }
}
```

Swagger `@Schema` 설명의 "최대 30자"·"150자 이하"는 **"이모지·자모 포함 사용자가 보는 글자 수 기준"**임을 명시하도록 문구를 보강한다.

## 도메인 모델

### 새 검증 애노테이션 (`global/common/validation`)

프로젝트 첫 커스텀 validator다. 특정 도메인에 속하지 않으므로 `global/common` 아래 `validation` 패키지를 새로 만든다(`form`·`pagination`과 같은 층).

| 구성요소 | 역할 |
|----------|------|
| `@GraphemeSize(max = N)` | 필드에 붙이는 제약. `null`은 통과(선택 입력 필드라 `@NotNull`과 조합해 쓴다) |
| `GraphemeSizeValidator` | `java.text.BreakIterator.getCharacterInstance()`로 경계를 세어 판정. 코드유닛 절대 상한(`max × 20`)을 함께 검사 |

- 로케일 무관하게 동작해야 하므로 `BreakIterator`는 **`Locale.ROOT`** 로 생성한다.
- 메시지 기본값은 `"{max}자 이하로 입력해주세요."` — 기존 Bean Validation 기본 메시지보다 사용자 노출에 적합하다.
- `@Size`는 이 두 필드에서 **제거**한다(둘을 함께 두면 더 빡빡한 `@Size`가 먼저 걸려 변경이 무의미해진다).

### 마이그레이션 V26

> V25(`member.course_tutorial_completed_at`)가 현재 최대 번호다.

| 테이블·컬럼 | 변경 | 이유 |
|-------------|------|------|
| `member.driving_goal` | `VARCHAR(30)` → `TEXT` | 30 grapheme이 코드포인트 30을 넘을 수 있다 |
| `review.content` | `VARCHAR(150)` → `TEXT` | 150 grapheme이 코드포인트 150을 넘을 수 있다 |

- **폭을 넓힌 `VARCHAR`가 아니라 `TEXT`인 이유**: grapheme 하나의 코드포인트 수에 상한이 없어 안전한 `VARCHAR(N)`을 고를 수 없다. 어떤 N을 잡아도 적법한 입력을 DB가 거절할 수 있다. 저장 크기는 위 비기능 요구사항의 **코드유닛 절대 상한**이 애플리케이션에서 책임진다. Postgres에서 `TEXT`와 `VARCHAR(N)`은 저장 방식·성능이 동일하다.
- 두 컬럼 모두 **확장 방향**이라 기존 데이터 손실·재작성이 없다. 인덱스도 걸려 있지 않다.
- 엔티티의 `@Column(length = ...)`도 함께 정리한다 — `Member.drivingGoal`, `Review.content`(`length = MAX_CONTENT_LENGTH` 제거, `columnDefinition = "text"`). `Review.MAX_CONTENT_LENGTH` 상수는 **grapheme 한도**로 의미가 바뀐 채 유지한다(`@GraphemeSize(max = Review.MAX_CONTENT_LENGTH)`).

## 구현 노트

- **`BreakIterator`가 이모지 시퀀스를 제대로 묶는지 먼저 확인했다.** JDK 버전에 따라 ZWJ·국기·피부톤을 쪼개는 구현이 있어 설계 전제였다. 프로젝트 툴체인인 **JDK 21.0.2**에서 한글·😀·❤️·👍🏻·👨‍👩‍👧‍👦·🇰🇷·👩‍💻·결합 악센트 모두 **1로 세는 것을 확인**했다(`Pattern`의 `\X`도 동일 결과라 대안으로 남겨둔다).
- 검증 순서는 **코드유닛 상한 → grapheme 카운트**다. 부풀린 입력을 경계 순회 전에 잘라내며, 정상 입력은 상한에 걸릴 수 없다.
- `BreakIterator`는 스레드 안전하지 않아 판정마다 새로 만든다. 로케일에 따라 경계 규칙이 흔들리지 않도록 `Locale.ROOT`로 고정했다.
- 상수 위치는 기존 관례를 따랐다 — 후기는 `Review.MAX_CONTENT_LENGTH`(의미만 grapheme으로 바뀜), 운전 목표는 새로 `Member.DRIVING_GOAL_MAX_LENGTH`를 두고 수정·온보딩 두 DTO가 공유한다.
- `OnboardingRequest.practiceTypes`의 `@Size(max = 3)`은 **그대로 둔다** — 컬렉션 개수 제한이라 문자 수와 무관하다.

## 미해결 질문

1. *(미해결)* **후기 주의사항(`caution`)** — 지금 길이 제한이 **아예 없다**(DTO 무제약 + `TEXT`). 이번에 함께 한도를 둘지, 아니면 무제한을 유지할지. 디자인에 정해진 글자 수가 있으면 알려주면 같이 반영한다.
2. *(`×20`으로 구현, 조정 가능)* **코드유닛 절대 상한 배수(`max × 20`)** — 가족 이모지가 11 code unit이라 20배면 충분한 여유지만, 더 조이거나(×12) 아예 두지 않는 선택도 가능하다. 이 값으로 확정할지 확인이 필요하다.
3. *(미해결)* **나머지 텍스트 필드 확장 시점** — 신고 상세·미방문 사유·최근검색 표시명·코스명/설명/주의사항을 언제 같은 기준으로 옮길지. 지금은 범위 밖으로 두었지만, 앱에서 이모지 입력이 가능한 필드가 더 있다면 QA에서 같은 리포트가 반복된다.
